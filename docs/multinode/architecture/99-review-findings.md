# Anexo — Revisión adversarial del diseño multi-nodo

Hallazgos de la fase de revisión (5 lentes: HA, seguridad, consistencia, escala, coherencia). Todos fueron incorporados en la fase de endurecimiento de cada sección; este anexo es la trazabilidad.

**Totales:** 48 — 10 blocker · 25 high · 11 medium · 2 low

## BLOCKER (10)

- **[observability-ops, control-plane, data-model]** _(reliability-ha)_ — Self-fencing keyed to a non-HA control plane backed by a SINGLE Postgres turns any control-plane hiccup into a fleet-wide VM kill. Observability §3(a) has every agent SIGKILL all its local QEMU at AGENT_SELFFENCE_AT=12s if it cannot renew its lease, and the lease authority is the master, whose authoritative store is one Postgres on the master (data-model ADR-1, 'control-plane SPOF until Phase 5'). Therefore a transient master restart, leader-election failover gap, LB blip, or Postgres pause longer than ~12s causes EVERY node simultaneously to fail lease renewal and self-destruct EVERY running desktop in the cluster. A control-plane outage must never kill running guests; this design makes the control plane a single point of total data loss, which inverts the stated HA goal.
  - → Decouple guest liveness from control-plane reachability. Self-fence must NOT fire merely because the master/DB is unreachable. Options: (1) only self-fence when the agent can still positively confirm it has lost a contested resource (shared-storage lock revoked / epoch superseded), never on bare lease timeout; (2) require the master HA quorum (multiple coordinators + replicated/clustered Postgres) to exist BEFORE enabling lease-based self-fencing, and gate auto-fence on the storage tier — Tier-L (local-disk) VMs cannot be double-run on shared media, so they should keep running through a control-plane outage rather than being killed. The timing proof must hold across a master leader failover, not just a clean single-master run.
- **[control-plane, observability-ops]** _(reliability-ha)_ — Two sections specify mutually exclusive heartbeat models. Control-plane §7 + ADR-CP4 mandate MASTER-PULL ('master polls agents... agents need no master-discovery for liveness') and explicitly reject agent push. Observability §1 + ADR-2 mandate AGENT-PUSH ('agent→master push (not master poll)') and explicitly reject master polling. This is not a cosmetic clash: the entire fencing/split-brain safety argument (self-fencing lease watchdog, ADR-1) is built on the heartbeat BEING the agent-driven lease renewal. Under the control-plane's pull model the agent has no lease to fail to renew and CANNOT self-fence, so the no-double-run invariant collapses. Cadence constants also diverge (≈15s/miss×3≈45s detection vs 5s/LEASE_TTL=15s/declare-dead 20s).
  - → Pick one model cluster-wide and reconcile both ADRs. The fencing design requires agent-push lease renewal, so adopt push and rewrite control-plane §7/ADR-CP4 accordingly (a pulled heartbeat is fundamentally incompatible with a watchdog self-fence). Unify the timing constants in one place (HEARTBEAT_INTERVAL, LEASE_TTL, AGENT_SELFFENCE_AT, MASTER_DECLARE_DEAD, NODE_STALE_AFTER_MS) and have both sections reference it.
- **[observability-ops, control-plane]** _(reliability-ha)_ — HA-restart/evacuation bypasses the exactly-once machinery and is not crash-safe, enabling double-run on two HEALTHY nodes. Observability §4 'dispatch createVM+start on the target agent' is a direct dispatch, not an enqueue through the CommandOutbox/NodeCommand idempotency path (control-plane §4). Meanwhile control-plane ADR-CP3 makes leadership a PER-TICK advisory lock (withLeadership acquires+releases each tick), so there is no stable leader across ticks and 'split-second double-run windows at failover are tolerated because every job is idempotent.' Evacuation is a multi-step, minutes-long, NON-idempotent operation (fence → confirm → place → create+start), with no persisted resumable journal. Two interleaving tick-leaders, or a leader crash mid-evacuation, can each run chooseNodeForMachine for the same dead-node VM and start it on two different live targets — concurrent writers on shared storage / duplicate L2 identity.
  - → Route every HA-restart through CommandOutbox with a deterministic-per-attempt idempotencyKey = hash(machineId, fenceEpoch) so re-dispatch is deduped and a stale-epoch start is rejected. Persist the evacuation as a state machine (FenceAction + per-VM evacuation rows / Node.liveness column) so a new leader resumes rather than restarts the plan. Do not wrap a long evacuation in a single per-tick advisory lock; give fencing/evacuation a held-leadership session whose loss aborts in-flight side effects, and make each step idempotent like MigrationJob already is.
- **[onboarding-pki, security-rbac]** _(security)_ — The SAS anti-MITM proof is unsound: it is grindable. sas6 = uint32_be(SHA256(tag||nodeKeyFp||masterCaFp||nonce)) mod 1e6 is only ~20 bits, there is NO commitment round, and a terminating MITM learns every input it needs (the node's CSR pubkey fp, the real master CA fp, and the relayed nonce) BEFORE it must choose the CA it substitutes toward the node. The attacker relays the node's real CSR to the master (so the master's csrFp matches), computes the master's target 6-digit value exactly, then grinds candidate CA certs (vary serial/validity/key — microseconds each, ~1e6 tries) until SHA256(tag||nodeKeyFp||attackerCaFp||nonce) mod 1e6 == target. Now BOTH screens show the same code while the node pins the attacker's CA. The MITM then re-signs the node's CSR with its own CA (node validates it, since it trusts attacker CA), supplies its own masterServerFp, and holds simultaneous mTLS to both real master and node. The claim 'codes match only if both fingerprints are genuine' is false. ADR-PKI-2 protects only against a code-relay attack, not key-substitution-plus-grind, which is the actual MITM.
  - → SAS over independently-grindable public keys with no commitment is broken at 20 bits. Either (a) make the human out-of-band comparison of the FULL master CA fingerprint mandatory and the actual root of trust (read from the master's own console / provisioning channel, compared digit-for-digit against what the node derived), and demote the 6-digit SAS to UX convenience only — stop claiming it defeats MITM; or (b) add a real commitment protocol: master commits H(CA||nonce) and node commits H(nodeKey||nonce) and both are exchanged/displayed BEFORE either reveals, so neither side can adapt its key after seeing the other's; or (c) bind the CA fingerprint into an out-of-band channel (printed on the master, entered on the node) rather than learned over the spoofable mDNS/HTTP path. Do not ship the current SAS as the MITM control.
- **[control-plane, data-model]** _(data-consistency)_ — Two divergent, incompatible command-outbox models are specified for the SAME master→agent channel. Control-plane §4 defines `NodeCommand` (states pending|inflight|acked|failed, `id == idempotency_key`, NO sequence column, NO lease, NO expectVersion) drained by a single leader-elected command pump (§6). Data-model defines `CommandOutbox` (states pending|leased|dispatched|acked|failed|dead, monotonic `seq` BigInt, `idempotencyKey @unique`, `leaseOwner`/`leaseExpiry`, `expectVersion`) drained by N concurrent dispatchers via SKIP LOCKED. They disagree on the table, the state set, the concurrency model, and the ordering guarantee. NodeCommand has no `seq`, so under the leader-pump it has no defined per-machine FIFO; CommandOutbox's per-machineId FIFO under SKIP LOCKED requires every lease to scan for older un-acked rows. As written, the two sections will be implemented as two different pipelines with different delivery semantics.
  - → Collapse to ONE outbox model. Adopt `CommandOutbox` (it strictly dominates: seq + lease + expectVersion + dead state). Pick ONE concurrency model: either leader-gated single pump (simplest FIFO, matches ADR-CP3) OR SKIP-LOCKED multi-dispatcher — not both. If multi-dispatcher, the lease predicate must explicitly exclude leasing any row whose machine has an older row in {pending,leased,dispatched} (un-acked AND un-dead), and that must be stated, not implied. Delete the `NodeCommand` schema.
- **[control-plane, observability-ops]** _(data-consistency)_ — Direct heartbeat-direction contradiction with a safety-proof dependency. Control-plane §7 + ADR-CP4 decide PULL: 'Heartbeat is master-pull, not agent-push: the command pump's leader calls Heartbeat() on each node.' Observability §1 + ADR-2 decide PUSH: 'The heartbeat is agent→master push (not master poll)' and the entire self-fencing/STONITH safety argument (AGENT_SELFFENCE_AT < MASTER_DECLARE_DEAD) depends on the agent renewing a lease via its own outbound heartbeat. A pull model cannot drive a self-fencing lease — the agent has no locally-armed renewal deadline, so a partitioned-but-alive node never self-fences and the 'no double-run' invariant collapses. The desired-vs-observed reconcile feed (vms[]) and `Node.lastHeartbeat` update are also attributed to opposite ends.
  - → Choose PUSH and rewrite ADR-CP4 as rejected. The self-fencing lease (observability §3) is the load-bearing data-consistency guarantee and requires agent-initiated renewal; pull cannot provide it. Update control-plane §7 so the leader does NOT call Heartbeat() — instead it consumes pushed heartbeats and runs the miss-detector. Reconcile the lease epoch/TTL fields (observability) into the heartbeat message defined in control-plane.
- **[control-plane, observability-ops]** _(data-consistency)_ — Self-fence enumeration depends on the channel that the fence-triggering partition has already severed. ADR-CP1 states the agent has NO local DB and ALL reconcile reads (`findRunningVMs`, etc.) go over RPC to the master via `RpcDatabaseAdapter`. Observability §3 says on lease-renewal failure the agent must SIGKILL every local QEMU 'scoped to its own nodeId — findRunningVMs({nodeId}) reap only this node's VMs.' But the trigger for self-fencing is precisely that the master is unreachable (partition / master down), so the RPC-backed `findRunningVMs` cannot return — and per the same ADR-CP1 it must fail CLOSED (do not kill). A fail-closed enumeration during the fence window means the agent kills nothing, defeating self-fencing.
  - → Self-fence VM enumeration must be LOCAL-ONLY: scan /proc + pidfileDir for QEMU PIDs the agent itself launched (the agent already owns its pidfiles under pidfileDir, InfinizationService.ts:27-33), never the RPC DB adapter. Explicitly carve out a local-pidfile enumeration path used only for self-fencing and orphan-of-own-pidfile reaping, distinct from the DB-backed reconcile. State that this local path is the fence's source of truth precisely because it has zero master dependency.
- **[control-plane, observability-ops]** _(scale-performance)_ — The two subsystems specify mutually contradictory heartbeat designs, and the contradiction has opposite scale characteristics. Control-Plane §7 + ADR-CP4 mandate a MASTER-PULL model at HEARTBEAT_INTERVAL ≈15s, executed serially by the single leader-elected command-pump. Observability §1 + ADR-2 mandate an AGENT-PUSH model at HEARTBEAT_INTERVAL=5s that doubles as the self-fencing lease renewal. These cannot both hold: a pull model cannot drive the watchdog self-fence (the agent must locally know its renew-by deadline, which only push gives it), and 5s vs 15s changes NODE_STALE_AFTER_MS, fence timing (AGENT_SELFFENCE_AT<MASTER_DECLARE_DEAD), and detection-latency SLOs. A pull model from one leader is also O(nodes) serial RPC on a single process and goes blind during a master-side partition.
  - → Pick agent-PUSH (Observability's model) cluster-wide; it is required for the lease/STONITH safety proof and scales as fan-IN rather than a single leader's serial fan-out. Delete the master-pull text in Control-Plane §7/ADR-CP4 and re-derive HEARTBEAT_INTERVAL, lease TTL, and fence margins from one constant. Decouple the lease-renewal RPC (tiny, every 5s) from the heavier metrics+vms[] drift payload (every 15-30s) so the high-frequency path stays cheap.
- **[control-plane, observability-ops]** _(operability-coherence)_ — Heartbeat direction is specified twice, incompatibly. Control-Plane §7 + ADR-CP4 decide master-PULL ('Heartbeat is master-pull, not agent-push... the command pump's leader calls Heartbeat() on each node') and explicitly reject push. Observability §1 + ADR-2 decide agent→master PUSH ('The heartbeat is agent→master push (not master poll)... a push doubles as the lease renewal') and explicitly reject poll. The entire Observability fencing model (self-fencing watchdog armed on lease-renewal-FAILURE) is only meaningful with push: a pull model gives the agent no renewal event to miss, so the watchdog can never arm. The two sections cannot both ship.
  - → Pick one model and make every dependent section consistent. Push is the only one that supports the lease/self-fence safety property and lets the agent observe /proc; adopt push, delete the pull text and the 'command pump leader calls Heartbeat()' mechanism in Control-Plane §7/ADR-CP4, and re-base the leader-gated loop on ingesting pushed frames. Unify HeartbeatRequest/HeartbeatResponse as the single schema (see related outbox/payload findings).
- **[control-plane, observability-ops]** _(operability-coherence)_ — Directly opposite behavior for the SAME failure (network partition, agent alive). Control-Plane ADR-CP4 Consequences: 'a partitioned-but-alive agent keeps its VMs running (correct — no cross-node reaping)... simply reads offline until the partition heals.' Observability §3(a): the agent self-fences and 'SIGKILL every local QEMU' at AGENT_SELFFENCE_AT=12s when it cannot renew its lease (i.e. exactly a partition). One section guarantees the desktops survive a partition; the other guarantees they are all killed. This is a core correctness/availability contradiction, not a detail.
  - → Reconcile the partition policy explicitly and per storage tier. Self-fencing is required for shared-storage single-writer safety but is destructive for local-storage VDI desktops that are perfectly safe to keep running. Make self-fence conditional on Tier-S (shared) VMs only, and have Control-Plane ADR-CP4 cite that exception instead of a blanket 'keeps running'. Document the resulting availability trade-off in one place.

## HIGH (25)

- **[observability-ops]** _(reliability-ha)_ — Self-fencing is treated as 'primary, always on' but is NOT actually a fence without a hardware watchdog, which the design lists as merely 'ideally' / 'where available' (softdog). A self-fence implemented as an in-process monotonic timer is never serviced by a wedged-but-not-dead process (kernel GC stall, D-state I/O hang, paused container). In that exact state the QEMU children keep running and writing disk/holding IPs, the agent stops heartbeating, the master declares dead at 20s, and HA-restart fires elsewhere → split-brain. So for any no-BMC, no-watchdog deployment (explicitly a supported single-NIC/local-storage profile) there is effectively NO fence.
  - → Make a hardware or softdog /dev/watchdog MANDATORY for enabling HA-restart, and have the master refuse to auto-evacuate a node that lacks a confirmed fence path (BMC/PDU or armed watchdog). When neither positive-fence nor watchdog is present, HA-restart must be operator-gated (confirmFence), never automatic. Surface 'fenceable: false' in node inventory and block auto-evacuation policy on it.
- **[observability-ops]** _(reliability-ha)_ — The fencing timing inequality AGENT_SELFFENCE_AT(12s) < MASTER_DECLARE_DEAD(20s) is presented as 'a provable safety property,' but the two timers run on DIFFERENT clocks measured from DIFFERENT events. The master measures staleness as wall_now − lastHeartbeat (lastHeartbeat = master clock at receipt), while the agent arms its watchdog from its own monotonic clock at ACK receipt. The proof silently assumes both started at the same instant and the same clock; it does not account for master↔agent clock skew, the network δ between agent-send and master-write, or — critically — a master LEADER FAILOVER where the new leader inherits lastHeartbeat written by the dead leader and may have its own clock offset. The 8s nominal margin is consumed by skew + RTT and is unquantified.
  - → State and enforce the margin budget explicitly: MASTER_DECLARE_DEAD − AGENT_SELFFENCE_AT must exceed (max tolerated clock skew + max heartbeat RTT + new-leader takeover delay). Use the heartbeat's clockUnixMs to reject/penalize nodes whose skew exceeds the budget (do not just 'detect' it — refuse to HA-evacuate when skew is unknown/large). Add a mandatory post-failover grace period during which a freshly elected leader withholds dead-declarations for at least LEASE_TTL so it cannot evacuate based on a predecessor's timestamps.
- **[migration, control-plane]** _(reliability-ha)_ — A VM in mid-migration is invisible to BOTH nodes' node-scoped reconcile, leaking the incoming QEMU. During prepareIncoming the target launches a paused QEMU for a machine whose Machine.nodeId is still the SOURCE (nodeId flips only at switchover, I3). The target's node-scoped findRunningVMs(targetNodeId)/attachToRunningVMs(targetNodeId) (G0 fix) therefore do NOT see it, and the target's orphan reaper treats it as foreign (nodeId≠self) so it is never cleaned up. If the target agent crashes/restarts mid-migration, that incoming QEMU becomes an unmanaged, un-reapable process pinning the migration port, NBD export, and destination disk — neither node owns it, and only a retried RPC is fenced (I4), not the leaked process.
  - → Make reconcile MigrationJob-aware: each agent, on attach/reconcile, must additionally consider VMs where it is the targetNodeId (or sourceNodeId) of a non-terminal MigrationJob, and reconcile incoming/outgoing QEMU against that job's phase + fence token. On agent restart with a non-terminal job for which it is the target and the job has not reached switchover, tear down the incoming QEMU and let the master re-drive from a clean state.
- **[migration]** _(reliability-ha)_ — The crash-recovery rule 'if the target is running the VM, finish-forward; otherwise roll back to source' (§7) is unsafe for non-shared (drive-mirror) live migration once the mirror has pivoted. The documented order is disks-ready → RAM-converged → block-job-complete (pivot) → cont(target). After block-job-complete, the SOURCE QEMU's block backend is pivoted to the target's NBD/disk; the source's local qcow2 is no longer authoritative. If the master crashes in the window after pivot but before cont(target), neither side is 'running' (source paused at pre-switchover, target paused at inmigrate), so the rule rolls back by re-cont'ing the source — but resuming the source now writes through a pivoted backend / against a disk the target also owns, i.e. a divergent or cross-node write. 'Who is running' is insufficient to disambiguate pre-pivot vs post-pivot.
  - → Persist a distinct sub-phase for the pivot (e.g. 'pivoted') before issuing block-job-complete, and make the reconciler key the finish-forward vs rollback decision on that flag, not only on getStatus. Post-pivot, the only safe resolution is finish-forward to the target (cont target, kill source); rollback-to-source is permitted only strictly before any block-job-complete. Verify via per-disk mirror job state on both agents before choosing.
- **[data-model, control-plane]** _(reliability-ha)_ — Deterministic idempotency keys silently suppress legitimate repeat operations. Data-model's worked example uses idempotencyKey=hash(machineId,'create') and control-plane §4 frames keys per operation type, yet keys are also said to equal the NodeCommand uuid id. If any per-operation-type deterministic key is used for non-create verbs, the agent's dedup LRU will treat a genuinely new intent as a replay: start VM (key h(m,'start')) → stop → start again (same key) → agent returns ALREADY_APPLIED and NEVER restarts the VM. The same hazard hits reboot/attachDisk. This is a correctness/availability bug (lost operation), the inverse of the double-run risk the keys exist to prevent.
  - → Idempotency keys must be per-command-INSTANCE (the CommandOutbox/NodeCommand uuid), not per (machineId, verb). Keep deterministic keys only where the intent itself is unique-once (createVM tied to a fresh machineId). Fix the data-model example so it does not show a content-derived key for a repeatable verb, and document that the agent dedup cache is keyed by command id, with TTL safely shorter than the minimum gap between distinct user intents.
- **[control-plane, data-model, security-rbac, observability-ops]** _(security)_ — The agent->master direction is not node-scoped. ADR-CP1 routes all agent DB access through an RpcDatabaseAdapter ('the agent never mutates the DB except through this proxy'), and the heartbeat carries vms[] + per-VM qmpStatus that the master folds straight into Machine.status writes. The node-scoping enforcement described everywhere is either the AGENT checking itself (security §5 invariant 1) or the master->agent NodeAgent service checking spec.node_id==self.nodeId (control-plane §3). Nothing states that the MASTER scopes proxied DB reads/writes and heartbeat-reported vm[] claims to the calling node's cert identity. Since the client cert CN==nodeId, a single compromised agent can call findMachineByInternalName / updateMachineStatus / report vms[] for OTHER nodes' machines: read the entire fleet's Machine table, flip another node's VM to 'off', or keep a dead peer's lastHeartbeat fresh to block fencing. This is a fleet-wide lateral-movement and integrity hole that the 'master is sole RBAC point' model does not actually close.
  - → Make the master derive nodeId from the verified mTLS client cert (CN) on EVERY agent-originated call and reject any RpcDatabaseAdapter operation or heartbeat whose machine.nodeId / claimed nodeId != cert nodeId. The proxy must be a node-scoped facade, not a transparent Prisma passthrough. Treat agent-supplied nodeId/vmId as untrusted; the cert is the only authority.
- **[security-rbac, deployment-installer, cross-cutting]** _(security)_ — Two sections specify mutually exclusive handling of INFINISERVICE_HMAC_MASTER_SECRET. Security-RBAC §1 and §4 place the fleet-wide master HMAC secret on EVERY node ('every host's root-only systemd EnvironmentFile') so a migrated VM's guest secret verifies. Deployment-Installer §8 says the opposite and safer thing: the master secret 'never lands on a node; per-VM HMAC keys are derived on the master and shipped just-in-time over mTLS at VM-create time.' The security-rbac approach means one compromised node yields the master secret and can forge host->guest commands for the ENTIRE fleet's VMs — directly contradicting the same document's blast-radius claim that 'a leaked guest secret forges for exactly one VM' and the ADR-S3 promise that a compromised node's blast radius is its own VMs only. The migration requirement does NOT justify the master secret on nodes: shipping the per-VM derived key to the destination node JIT solves it.
  - → Adopt the deployment-installer model everywhere: never distribute INFINISERVICE_HMAC_MASTER_SECRET to compute nodes. Derive HMAC(master, vmId) on the master and push only that per-VM key over the authenticated RPC to the node(s) currently hosting the VM (and to the destination at migration). Delete the secrets-at-rest rows that put the master secret on nodes and fix the §1 rationale.
- **[onboarding-pki, security-rbac, observability-ops]** _(security)_ — Decommission/revocation has no enforcement against a compromised or malicious node. The design relies on CRL + short leaf TTL: 'the node's mTLS handshakes then fail, and the agent tears down local QEMU.' But CRL only blocks NEW handshakes, and a compromised/decommissioned agent will not voluntarily tear down its QEMU. Worse, with the master-pull heartbeat model the master simply stops initiating — it has no channel to force teardown — so the rogue node keeps running VMs and, on Tier-S shared storage, keeps writing the same qcow2 the master may now re-home elsewhere (concurrent-writer corruption). G0 scoping prevents cross-node reaping but does nothing to stop a node from mauling its own tenants' data or holding a shared-storage disk. 'Revoked node cannot touch other nodes' VMs' is true but insufficient.
  - → decommissionNode (and the malicious-node case) must trigger positive fencing, not just CRL: storage-level eviction (Ceph RBD exclusive-lock blocklist / NFS lock break for the node's client), network quarantine (drop the node's VTEP from every department FDB and revoke its overlay membership), and BMC/PDU power-fence where available — the same STONITH machinery observability-ops §3 already defines. Tie decommission into that fencing path before declaring the node safely removed.
- **[migration, storage, security-rbac]** _(security)_ — The cross-node disk data channel's authentication/encryption is unspecified and inconsistent with the PKI. Migration §1 says agents talk to each other 'over the one TCP/NBD data channel the master tells them to open' and §3 has the target pull bytes 'straight from source over the mesh,' while also claiming it 'reuses the agent's existing mTLS socket' — but that mTLS socket is the master<->agent channel, and node certs are issued EKU clientAuth ONLY (onboarding §1/§7). An agent therefore cannot act as a TLS server to a peer agent under the current PKI, so the agent<->agent disk/NBD stream is left either unauthenticated/cleartext (raw NBD has no auth) or requires a cert capability the design forbade. Result: VM disk images (containing tenant secrets) streamed across the LAN with no peer authentication or confidentiality, open to passive exfiltration and active injection during importDisk. Storage §7's SHA-256 only gives integrity end-to-end, not channel auth or confidentiality.
  - → Define the peer data channel explicitly: either (a) proxy all cross-node disk bytes THROUGH the master over the existing master<->agent mTLS legs (never a direct agent<->agent socket), or (b) issue node certs with BOTH clientAuth and serverAuth and require mutual TLS + cert-pinning on the peer channel, with the master handing each side a short-lived, job-scoped token bound to the MigrationJob.id fence. NBD must run inside that TLS tunnel, bound to the management/overlay plane, never a routable interface.
- **[cross-cutting, control-plane, observability-ops]** _(security)_ — The heartbeat direction is specified two opposite ways, and the chosen direction is load-bearing for a safety/security property. Control-plane §7 + ADR-CP4: 'Heartbeat is master-pull, not agent-push.' Observability-ops §1 + ADR-2: 'agent->master push (not master poll)' and the entire no-double-run / split-brain fencing proof depends on the agent self-fencing when it cannot RENEW its lease (i.e., agent-initiated push). Under the control-plane master-pull model there is no agent-side lease renewal at all, so a partitioned-but-alive node never self-fences and the AGENT_SELFFENCE_AT < MASTER_DECLARE_DEAD inequality — the cornerstone of the corruption-safety argument — does not exist. The two subsystems would build incompatible liveness paths, and shipping the master-pull variant silently removes the only mechanism that prevents shared-storage double-writes after a partition.
  - → Resolve to a single model. Adopt agent-push lease-renewal heartbeat (required by the fencing proof), bind each heartbeat's nodeId/vms[] to the mTLS cert identity (see the node-scoping finding), and rewrite control-plane §7/ADR-CP4 to match. Keep a hardware/softdog watchdog so a wedged agent still self-fences.
- **[networking, security-rbac]** _(security)_ — Console gateway session authorization is underspecified, creating console-hijack and IDOR vectors. The browser reaches a VM display via wss://master/console/<sessionToken> with the sessionToken as a bearer secret embedded in the URL path. URLs leak (proxy/access logs, browser history, Referer), and there is no stated binding of the sessionToken to the requesting user's authenticated session, nor any check that getConsoleSession(vmId) verifies the caller actually holds console/vm:view permission on THAT vmId within their department scope. As written, anyone who obtains the URL can attach to a live SPICE/VNC session, and any authenticated user could request a console for an arbitrary vmId (IDOR across tenants). The QMP ticket being short-lived/single-use only protects the node<->gateway hop, not the browser<->gateway authz.
  - → Require the WS upgrade to carry the user's authenticated session (JWT) AND a single-use, short-TTL sessionToken passed out-of-URL (header / subprotocol), bound server-side to {userId, vmId, ticket}. Enforce the department-scope permission check on vmId at getConsoleSession time (reuse scopeCovers / vm:view), and revoke the session on stop/migrate as already planned. Never put the only authorization secret in the URL path.
- **[data-model, control-plane]** _(data-consistency)_ — Idempotency-key scheme is inconsistent AND unsafe for repeatable verbs. Control-plane §4 uses a per-instance UUID (`id` IS the idempotency_key). Data-model's create flow uses a content hash `idempotencyKey=hash(machineId,'create')`. If the content-hash scheme is generalized to repeatable verbs (Start/Stop/Reboot), then a legitimate Start issued after a prior Stop produces the SAME key as the earlier Start; the agent's dedup cache returns ALREADY_APPLIED and the VM is never started — a silently-dropped command. createVM happens to be naturally once-per-machine, masking the bug, but the two sections present two key schemes with no rule for which verbs use which.
  - → Make idempotency_key per-command-instance for all repeatable verbs (use the CommandOutbox row UUID / `id`, which is already `@unique`). Reserve content-addressed keys only for genuinely once-ever operations if at all. State the rule explicitly: dedup key identifies a command instance, not a (machine,verb) intent. This also makes the dedup-cache TTL reasoning sound.
- **[data-model, observability-ops]** _(data-consistency)_ — Desired power-state is not durably modeled — only transient command-intent is. Data-model declares 'Desired state = the highest-seq UNACKED CommandOutbox row' and 'Machine.status stays the OBSERVED power state.' Once a Start command is acked, its outbox row is acked and there is no durable record that the VM SHOULD be running. So when a running VM's QEMU later dies (observed→off via heartbeat), the reconciler has nothing to diff against to decide the VM has drifted from desired=running. HA-restart (observability §4) is gated on whole-NODE death + HaPolicy, but a single-VM crash on a healthy node has no desired-state anchor for the cross-node reconciler. The design conflates 'command in flight' with 'durable desired state.'
  - → Add a durable desired-power column (e.g. `Machine.desiredState: running|stopped`) set transactionally alongside enqueuing Start/Stop, separate from observed `Machine.status`. Define drift as observed != desired for machines with no in-flight command. HealthMonitor.handleCrashedVM already flips observed→off (HealthMonitor.ts:883); the reconciler should compare to `desiredState` to decide restart-vs-leave, rather than inferring intent from an emptied outbox.
- **[migration, data-model]** _(data-consistency)_ — Heartbeat-driven drift correction races the migration state machine over Machine.status with no coordination. Data-model: master 'ingests [heartbeat] in one transaction, updating ... any drifted Machine.status.' Migration §2/§7 writes Machine.status/phase transitions and flips nodeId at switchover. During an in-flight migration the source agent still reports the VM in its node-scoped vms[] (paused/running); the master's generic drift-corrector will overwrite the status the migration coordinator just wrote (e.g. revert 'activating'/internal state to source's observed 'paused'/'running'), corrupting the migration's own bookkeeping and potentially the I3 switchover ordering.
  - → Exclude machines with a non-null `Machine.migrationJobId` (the I4 fence token) from heartbeat-based status drift correction — while a migration owns the VM, the migration coordinator is the sole writer of Machine.status/nodeId. Heartbeat ingest may still update node liveness/metrics but must skip status reconciliation for fenced machines.
- **[migration, data-model]** _(data-consistency)_ — The optimistic-lock staleness guarantee for commands is undermined because migration's nodeId flip is not specified to bump Machine.version, and the flip itself is not stated to be optimistic-locked. Data-model claims `expectVersion` (Machine.version snapshot at enqueue) lets 'a stale command (machine migrated/deleted meanwhile) be rejected by the optimistic lock.' That only holds if migrating a VM increments Machine.version. Migration §1 I3 flips nodeId in the terminal-phase TX but never says it bumps version. If version is unchanged, a Start command enqueued against the pre-migration node still matches expectVersion and is considered fresh. (It is caught downstream only by the agent's `Machine.nodeId===self` assertion routing it to REJECTED, but the section advertises version as the primary staleness guard.)
  - → Require the nodeId-flip transaction to increment Machine.version (it is a logical state change), and perform it via the existing optimistic-lock path (PrismaAdapter.transitionVMStatus / version CAS, PrismaAdapter.ts:699-814) rather than a bare update. Document that version bump + expectVersion is the primary stale-command guard and the agent nodeId self-check is the backstop, not vice-versa.
- **[observability-ops, data-model, control-plane]** _(scale-performance)_ — Heartbeat ingest is a DB write-amplification hotspot. The heartbeat carries vms[] for every local VM and the master 'ingests this in one transaction, updating Node.lastHeartbeat and any drifted Machine.status' (data-model 'Desired vs observed'), folding each VmObservation through QMP_TO_DB_STATUS_MAP (observability §1). At 1000 VMs / 20 nodes / 5s push, that is 200 VM-state evaluations per second and a multi-row Machine UPDATE transaction (~50 rows) per node every 5s, plus a NodeMetrics upsert. Worse, observability §2 makes the master /metrics 're-export from DB', so every Prometheus scrape (default 15s) full-scans NodeMetrics + 1000 VM rows. Postgres is being used as a time-series store on the hot single-writer that all placement, migration, and command-pump transactions also contend on.
  - → Separate three concerns onto three cadences/stores: (1) liveness = lease epoch only, a single Node.lastHeartbeat/epoch write per node per beat (20 writes/5s, trivial); (2) live metrics (cpu/ram/rss) = in-memory on the master and exposed to Prometheus directly, NOT persisted to Postgres (or pushed to a real TSDB) — Prometheus is the retention layer; (3) drift reconciliation = only diff vms[] against DB and UPDATE the rows that actually changed, on a slower cadence, skipping the common no-drift case so steady state is read-only.
- **[storage]** _(scale-performance)_ — Golden-image pre-seed fan-out saturates the master NIC. Storage §4 'Pre-seed': on GoldenImage publish the master 'fans out a low-priority pullImage(digest) RPC to all online nodes', each pulling from 'the master-local store'. A Windows golden qcow2 is commonly 20-40GB; 20 nodes pulling concurrently from one source = 400-800GB of simultaneous egress through the master's single management NIC, starving the very control/heartbeat/console traffic that shares that plane (networking §6 puts console+RPC on management). 'low-priority' is asserted but no rate limit, concurrency cap, or distribution topology is specified.
  - → Add an explicit image-distribution scheduler: cap concurrent pulls (e.g. ≤2-3 nodes at once), per-stream and aggregate bandwidth limits, and stagger. Better, exploit content-addressing for tree/peer distribution — once a node holds digest D it becomes a valid source (the design already tracks Disk{path:'golden/<digest>', status:'present'} per node), so pulls fan out from O(log N) seeders instead of all-from-master. Keep pre-seed strictly opt-in/scoped to nodes whose labels match a pool that references the image (already stated) and never block placement on it (pull-on-demand is the floor).
- **[migration, observability-ops, scheduling]** _(scale-performance)_ — No migration concurrency limit anywhere. A maintenance drain (scheduling 'Rebalancing/DRS' + observability §6) or a node-death evacuation enumerates all of a node's ~50 VMs and migrates them; cold-copy streams each full overlay and live-migration runs auto-converge (which throttles guest vCPUs). LiveTuning.maxBandwidthBytes is per-migration only — 50 concurrent cold-copies still collectively saturate the source/target NICs and disks, and N concurrent auto-converge live migrations throttle many guests at once. There is no global or per-node cap, no queue, no admission control on simultaneous MigrationJobs.
  - → Introduce a master-side migration scheduler with explicit concurrency limits: max concurrent migrations per source node, per target node, and cluster-wide, plus an aggregate bandwidth budget per node that divides maxBandwidthBytes across in-flight jobs. Drain/evacuation should enqueue (largest-first ordering is already specified) and admit jobs against these limits rather than firing all at once. Surface queue depth via the existing infinibay_migration_phase metric.
- **[networking, control-plane]** _(scale-performance)_ — Console gateway: throughput ceiling and session-affinity gap under the N-replica master. Control-Plane §6 runs the master as N stateless replicas behind a LB; networking §5 + ADR-N3 put the master on the console DATA path, proxying (websockify-style) the SPICE/VNC binary stream, and store session→(node,port,ticket) in the master to mint a sessionToken. Two scale problems: (a) a Node.js single event loop proxying many multi-Mbps binary streams is CPU-bound — 100 concurrent desktops × several Mbps is a real ceiling; (b) the session map is per-replica in-memory, but the LB has no stated way to route the follow-up wss:// upgrade to the SAME replica that minted the token. ADR-N3 asserts 'horizontally shardable by sessionToken' with no mechanism.
  - → Specify session affinity: encode the owning replica (or a routable key) in the sessionToken and have the LB do token-based sticky routing, or externalize the session map to Postgres/Redis so any replica can serve the WS. For throughput, treat the console proxy as a horizontally-scaled tier (dedicated proxy workers, not the GraphQL event loop), cap concurrent sessions per worker, and keep it off the GraphQL replicas so a console burst can't stall the API.
- **[control-plane, observability-ops, storage]** _(operability-coherence)_ — The fail-closed reaper contract and the self-fence contract give opposite actions for the same trigger (master/DB unreachable). Control-Plane §1/§5/§8 repeatedly mandate: on RpcDatabaseAdapter/DB error the reaper 'fails closed — never kills an unverified PID'. Observability §3 mandates: on lease-renewal failure (master unreachable) the agent SIGKILLs all local QEMU. Master-unreachable is the same condition. Worse: the agent has NO local DB (ADR-CP1), so during the partition it cannot run node-scoped findRunningVMs({nodeId}) to decide WHICH PIDs are 'its own' — the very scoping the kill is said to rely on is unavailable exactly when the kill fires.
  - → State that self-fence does not consult the DB: since there is one agent per host, every local QEMU under the agent's pidfileDir is by construction this node's, so the agent can SIGKILL from local pidfiles/proc without an RPC read. Then carve the contradiction explicitly: 'reaper fails closed on DB error' applies to the orphan-classification path; 'self-fence kills unconditionally' applies to the lease-loss path — and (per prior finding) gate the latter to shared-storage VMs.
- **[control-plane, data-model]** _(operability-coherence)_ — The master→agent command outbox is modeled twice with divergent schemas and state machines. Control-Plane §4 defines model NodeCommand (states pending|inflight|acked|failed, id == idempotency_key, no seq, no lease). Data-Model defines model CommandOutbox (states pending|leased|dispatched|acked|failed|dead, BigInt seq for per-machine FIFO, separate idempotencyKey @unique, leaseOwner/leaseExpiry, expectVersion). Data-Model says it 'supersedes legacy PendingCommand' but never reconciles with NodeCommand. A reader cannot tell which table/state-machine the dispatcher and the agent dedup cache actually use.
  - → Delete NodeCommand from Control-Plane §4 and make it reference Data-Model's CommandOutbox as the single owner, or vice-versa. Align the command pump (§6), the at-least-once delivery semantics (§4), and the agent dedup journal against ONE set of field names and states (notably: is the wire idempotency_key the row id or a separate column? FIFO via seq or not?).
- **[data-model, control-plane, observability-ops]** _(operability-coherence)_ — Single-host 'master is just a 1-node cluster' is broken by heartbeat-derived staleness. Data-Model backfill sets the master-local Node to status='online', lastHeartbeat=now() ONCE at migration. Every section then redefines nodeHealth/schedulable to require now()-lastHeartbeat <= NODE_STALE_AFTER_MS (15s). But the master's local Infinization is in-process (Control-Plane §1 fast-path) and never sends an RPC heartbeat, so nothing refreshes its lastHeartbeat. After 15s the master node reads stale → schedulable=false → NodePlacementService excludes it → a single-host install can no longer place any VM. No section owns refreshing the local node's liveness.
  - → Assign ownership: have the leader-gated loop (Control-Plane §6) write lastHeartbeat=now() for the master-local node every interval from the in-process agent's own /proc view, OR special-case nodeHealth so a node with address='127.0.0.1'/role='master' is liveness-exempt. State this in the same section that owns the nodeHealth rewrite, and add it to the single-host regression checklist.
- **[control-plane, onboarding-pki, deployment-installer]** _(operability-coherence)_ — N stateless master replicas (Control-Plane §6 HA) collide with the single-CA-key invariant. Onboarding §7 and Deployment ADR-D4 mandate the CA private key 'lives only on the master' (/var/lib/infinibay/pki/ca.key, root 0600, never in DB). But approveNode (Onboarding) and rotateNodeCert sign CSRs and therefore need ca.key on whichever replica handles the GraphQL mutation. With N replicas behind a LB, either every replica holds ca.key (contradicts 'only on the master', multiplies crown-jewel exposure) or signing must be pinned to one replica. Likewise agents pin the master SERVER cert — every replica needs an identity the agents trust. No section reconciles 'N replicas' with 'one CA host'.
  - → Define the CA/replica topology explicitly: e.g. ca.key lives on a single designated replica/host and signing operations are leader-gated (reuse the pg_advisory_lock leader from §6) so only the leader signs; all replicas share the same master server cert (issued from the CA, SAN = LB VIP) so agent pinning holds across replicas. State where ca.key physically resides under HA and how a replica without it handles approveNode (proxy to leader / reject).
- **[data-model, observability-ops]** _(operability-coherence)_ — Observability introduces persistent state that the data-model owner never declares. §3 uses Node.epoch ('bumped by the master on every lease grant and persisted'; returning zombie sees stale epoch) and a FenceAction row, and §5 emits infinibay_fence_total from it. Data-Model is the declared schema owner but its Node model has no epoch column and there is no FenceAction/MigrationJob-adjacent table for fence audit. These are load-bearing for the no-double-run proof yet unowned in the schema.
  - → Add epoch Int (or BigInt) to the Node model and a FenceAction model (nodeId, method, confirmedDown, epoch, at, actor) in the Data-Model schema-evolution block, and reference them from Observability rather than introducing them ad hoc. Specify epoch's relationship to the lease grant transaction.
- **[scheduling, migration]** _(operability-coherence)_ — Held-reservation TTL is shorter than the operation it must protect. Scheduling sets PlacementReservation.expiresAt = now()+120s and reaps expired held rows; it also pre-allocates a held reservation on each evacuation/migration target so the drain plan is 'capacity-consistent before any migration starts'. But cold-copy (Migration §3/Storage §1) streams gigabytes of overlay over NIC, and live precopy has a 10-min wall-clock budget — both routinely exceed 120s. The reservation expires mid-migration, the reaper frees it, a concurrent create double-books the target, and the migration lands into overcommit. The reservation's whole purpose (capacity-consistent multi-step placement) fails for exactly the multi-step case.
  - → Tie reservation lifetime to the operation, not a fixed 120s: when a reservation backs a MigrationJob, set expiresAt from the job (renewed on each progress/heartbeat tick) and only release on terminal job phase, or transition the reservation to a 'migrating' state the reaper ignores while MigrationJob.phase is non-terminal. Keep the 120s TTL only for the create-crash case.

## MEDIUM (11)

- **[data-model]** _(reliability-ha)_ — Per-machine FIFO on the outbox causes head-of-line blocking that can stall the very recovery/migration command needed. The dispatcher 'never leases a row whose machine has an older un-acked row.' If a node goes offline with a pending command for machine M, that row stays pending indefinitely (held until node returns or admin drains, per the failure table), which also blocks any later command for M — including a migrate/evacuate command issued to MOVE M off the dead node. So the FIFO discipline can deadlock recovery against the failure it is trying to recover from.
  - → Allow node-change/migration and cancel/teardown commands to preempt or supersede stale pending rows targeting a now-offline/dead node (e.g. mark superseded rows 'dead' when the machine's nodeId changes or the destination node is declared dead, using expectVersion to invalidate them), so per-machine FIFO is enforced only among commands addressed to the machine's CURRENT owning node, not across a node-death boundary.
- **[networking, security-rbac]** _(security)_ — VXLAN provides the cross-node department isolation that security-rbac §5 explicitly delegates to it, but VXLAN is unauthenticated and unencrypted. Any host on the overlay/underlay segment — including a single compromised compute node — can spoof the VTEP source IP and inject frames into ANY VNI (or sniff decapsulated tenant traffic), since the VNI is just a cleartext field and there is no per-frame authentication. nolearning + static FDB controls the control-plane MAC table but does nothing to filter spoofed INGRESS on UDP/4789. So the 'department = VNI = isolation boundary' claim does not hold against an attacker with underlay access, undermining multi-tenant separation across nodes.
  - → Encrypt/authenticate the overlay: run VXLAN inside IPsec or WireGuard between VTEPs (keys distributed by the master, rotated with node lifecycle), OR mandate a dedicated, access-controlled underlay VLAN with strict ingress filtering that accepts UDP/4789 only from known peer VTEP IPs and drops everything else. State the residual risk for single-NIC collapsed-plane deployments where this is weaker.
- **[security-rbac]** _(security)_ — The most security-critical actions are logged through a 'failure-swallowing' audit service. Security §6 reuses PolicyAuditService, explicitly described as append-only and failure-swallowing, for node.approved (root admission into the cluster — the trust root), node.decommissioned, and machine.migrated. If the audit write fails (DB pressure, transient error), the privileged action still proceeds with no record, and an attacker who can induce audit-write failures gets unlogged cluster-admission. There is also no tamper-evidence: a master DB compromise can rewrite the trust ledger.
  - → For trust-root transitions (approve/decommission/cert-revoke), make the audit write part of the same transaction as the state change (fail the operation if the audit row cannot be written) rather than fire-and-forget, and alert on audit-write failures. Consider hash-chaining the audit rows (each row includes H(prev)) for tamper-evidence independent of DB row-level mutability.
- **[data-model, control-plane]** _(data-consistency)_ — Dual command-ack authority. Data-model says heartbeat ingest marks 'commands acked/dead', while the dispatcher (both sections) marks a command acked on receiving OpResult. Two independent paths can transition the same CommandOutbox row to acked. A heartbeat that observes the desired end-state could mark a command acked even though the agent actually REJECTED/failed it (e.g. nodeId mismatch, or the end-state arrived via a different command), masking the failure and skipping retry/dead handling.
  - → Make the dispatcher's OpResult the SOLE authority for CommandOutbox lifecycle (acked/failed/dead). Restrict heartbeat ingest to liveness + observed-state drift detection; it must not transition command rows. If heartbeat observes a command's effect without an OpResult, treat that as drift to be reconciled, not as an ack.
- **[control-plane, data-model]** _(data-consistency)_ — Agent dedup-cache TTL is coupled to an unbounded outbox-pending lifetime, creating a re-apply window for long-offline nodes. Control-plane §4 says dedup keys 'expire after a TTL well beyond the command pump's retry horizon.' But data-model's failure table says an offline node's outbox rows stay `pending` 'until back, or admin drains' — an unbounded interval that can exceed any fixed dedup TTL. After TTL expiry, redelivery of a still-pending command finds no dedup entry and re-applies. For idempotent-ish verbs this is tolerable, but for createVM a stale-but-still-pending command after dedup expiry could spawn a duplicate VM unless the apply re-checks local existence.
  - → Do not rely on the dedup cache for createVM safety: the agent must make createVM idempotent against LOCAL state (findMachineByInternalName scoped to nodeId, plus pidfile presence) so a re-apply after dedup-TTL expiry is a no-op regardless of cache contents. Separately, cap how long an outbox row may remain `pending` to a node (move to `dead`/alert past a bound) so the pending lifetime and dedup TTL are not unboundedly decoupled.
- **[data-model, security-rbac]** _(scale-performance)_ — Append-only tables grow unbounded with no retention/partitioning. CommandOutbox accumulates acked/dead rows (4+ writes per VM op; a single pool refill of hundreds of VMs churns the table), AuditEvent and PolicyAuditLog are append-only by design, and NodeMetrics (if persisted, see separate finding) grows per-heartbeat. At sustained cluster op rates over months this bloats the hot single-writer Postgres and its indexes (the @@index[nodeId,status,seq] the dispatcher polls degrades as dead tuples accumulate).
  - → Define retention: move acked CommandOutbox rows to a periodic archival/delete job (or time-partition the table and drop old partitions), partition AuditEvent/metrics by month, and ensure autovacuum is tuned for the high-churn outbox. State the dispatcher poll should use a partial index on status IN ('pending','leased') so it never scans acked history.
- **[scheduling]** _(scale-performance)_ — Mass-create placement serializes on the Node row lock and recomputes capacity from scratch each time. ADR-S1 takes SELECT ... FOR UPDATE on the candidate Node row, and capacityWithReservations recomputes reserved = Σ Machines + Σ held reservations on that node per placement. During a pool refill of hundreds of desktops with spread+anti-affinity (at most one new pool VM per node per round), placements onto the same node queue behind the lock, and each holder re-aggregates over that node's ~50 existing Machine rows. Cost is O(placements × VMs_per_node) of locked aggregation on the hot writer.
  - → Maintain a denormalized per-node reserved-capacity counter (updated transactionally on commit/release of reservations and Machine create/delete) so the locked critical section reads one row instead of aggregating, shrinking lock hold time. Consider batch placement for pool refill (compute a spread plan for the whole batch under one pass) rather than N independent locked place() calls.
- **[control-plane]** _(scale-performance)_ — Single leader is a throughput bottleneck for all cluster-wide work. ADR-CP3 gates the command pump, reconcile loop, and every cron behind pg_try_advisory_lock, but the design then runs the command pump (draining every node's outbox) and — per Control-Plane §7 — the heartbeat pull on ONE elected replica. At 1000 VMs the dispatch/reconcile load all lands on a single process while the other N-1 replicas serve only read GraphQL; there is no sharding of the outbox drain across replicas by nodeId.
  - → Shard the command pump: use one advisory key per node-bucket (e.g. hash(nodeId) mod K) so up to K replicas each lead a disjoint slice of nodes and drain in parallel, rather than a single global pump leader. This also bounds blast radius if one replica stalls. (Moving to push-heartbeat per the blocker finding removes the serial pull load from the leader entirely.)
- **[control-plane, networking]** _(operability-coherence)_ — Console gateway statefulness is unreconciled with N stateless replicas. Control-Plane §6 runs the master as N stateless replicas behind a LB. Networking ADR-N3 has the master terminate the browser WebSocket and hold per-session state session→(node,port,ticket), bridging SPICE/VNC; it asserts the gateway is 'stateless per-session and horizontally shardable by sessionToken' but never says where the session map lives or how the LB routes the follow-up wss:// connect to the replica that minted the token. A normal LB will land the WS on a different replica that has no session entry.
  - → Specify the session-routing mechanism: either persist console sessions (sessionToken→node,port,ticket,exp) in Postgres so any replica can serve the WS, or require WS-sticky/affinity routing keyed on sessionToken at the LB. Name the owner (Networking) and note the LB requirement in Deployment.
- **[networking, onboarding-pki, data-model]** _(operability-coherence)_ — NodeUnderlay.vtepIp has no populating owner. Networking introduces model NodeUnderlay (vtepIp, the VXLAN VTEP address) and states 'Node onboarding populates NodeUnderlay.vtepIp', but Onboarding's JoinRequest/hardware payload and approve flow never mention a VTEP/underlay IP, and Data-Model's schema block doesn't include NodeUnderlay. So the overlay's per-node VTEP address — required before any cross-node department works — is declared by Networking but set by nobody.
  - → Add NodeUnderlay to the Data-Model schema and have Onboarding's JoinRequest carry the candidate underlay/data-NIC IP (or the agent report it on first heartbeat), with master persisting it. For single-NIC nodes default vtepIp=mgmtIp as Networking already notes. Make ownership explicit in one section.
- **[control-plane, observability-ops]** _(operability-coherence)_ — Heartbeat cadence and detection-latency constants conflict across sections. Control-Plane §7 uses HEARTBEAT_INTERVAL ≈15s, HEARTBEAT_MISS_LIMIT=3 → ~45s to flip offline. Observability §1/§3 uses HEARTBEAT_INTERVAL=5s, NODE_STALE_AFTER_MS=15s, AGENT_SELFFENCE_AT=12s, MASTER_DECLARE_DEAD=20s, and an SLO of ≤20s detection. The fencing safety inequality (AGENT_SELFFENCE_AT < MASTER_DECLARE_DEAD) and the SLO are all derived from the 5s value; the Control-Plane 15s/45s numbers silently violate the ≤20s SLO and weren't reconciled with the fence margins.
  - → Adopt one set of constants (the Observability 5s/15s/12s/20s set, since the fence proof depends on it) and delete the Control-Plane 15s/×3 values. Define them once (a shared constants block) and reference everywhere.

## LOW (2)

- **[control-plane, data-model, scheduling, observability-ops]** _(operability-coherence)_ — The nodeHealth/NodeCapacity rewrite (lastHeartbeat-based staleness + schedulable requiring status∈{approved,online}) is independently respecified by four sections (Control-Plane §7, Data-Model 'Desired vs observed', Scheduling capacity, Observability §1 with concrete code). They mostly agree but differ in return-type granularity ('online'|'stale'|'offline' vs boolean) and in whether 'approved' counts as schedulable. Four owners of one function invites drift during implementation.
  - → Designate Observability §1 (which has the concrete code) as the single owner of nodeHealth/NODE_STALE_AFTER_MS and have the other three sections reference it. Resolve the one real semantic question — is a node in status='approved' (paired but pre-first-heartbeat) schedulable? — in that one place.
- **[deployment-installer, observability-ops]** _(operability-coherence)_ — Day-2 runbook UX gaps for the dead-node and upgrade paths. Deployment §8 documents decommission as './run.sh decommission' run ON the node (cordon→drain→lxc stop), but a dead/partitioned node cannot run that command, and Observability's fence/confirmFence path for a dead node isn't wired to a decommission runbook. Separately, Deployment §8 references './run.sh join --upgrade' but the join dispatcher case in §2 parses no --upgrade flag.
  - → Add a master-side dead-node decommission runbook (decommissionNode(id) + confirmFence, no node shell required) distinct from the graceful node-side path, and add --upgrade parsing to the run.sh join case (or document the re-provision command actually used). Cross-link the Observability fence-confirm step to the decommission flow.
